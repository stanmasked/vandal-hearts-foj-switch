# Stage 171 — bind operator observations to exact generated NRO build

**Research-only. No real Nintendo Switch launch has been observed or
attested, and no original Flames of Judgment PS3 resources are included.**

Earlier stages independently established a bounded CPU boot trace
(stage 168), two-run recovery comparison (stage 169), manual
association with a stage-166 screen observation (stage 170), and a
fixed generated-only SD ZIP package (stage 165).

Stage 171 adds **build-byte identity** across those independent
records, without pretending a SHA-256 checksum proves what the
console executed or displayed.

## CI research build receipt

Every successful native devkitA64/UAM CI run now includes:

    build/foj-stage171-ci-build-receipt.json

in the `foj-gpu-native-research` artifact, along with the existing
`foj-stage165-gpu-sd-smoke.zip`. The receipt is created **only
after** the fixed-content SD archive is structurally validated.
It records exactly:

- CI commit SHA and numeric GitHub Actions run ID.
- SHA-256 of the entire generated-only SD ZIP.
- SHA-256 of exactly four generated executable artifacts inside that
  ZIP: clear NRO, triangle-research NRO, vertex DKSH and fragment DKSH.
- Explicit `switch_hardware_verified: false` and
  `original_foj_assets_included: false` declarations.

No user-owned PS3 image, game file, screenshot, secret, filesystem
path, hardware fingerprint, SD contents or individual user's
personal data are included. The receipt is **not signed** and cannot
authenticate a remote CI server by itself; it only detects byte-level
mismatches between the supplied package and declared receipt.

When needed, a local research build can create its own NEW receipt:

    python3 -m tools.foj_stage171_build_identity \
      --bundle ./foj-stage165-gpu-sd-smoke.zip \
      --create-receipt ./my-generated-build-receipt.json \
      --git-commit <40-lowercase-hex-commit> --run-id <positive-CI-run-id>

The supplied commit/run values are metadata declarations, not
independently verified against GitHub. Never put private user files
in this research-only ZIP.

## Compare a specific build with manual results

After physical observations **really occurred**, use the private
stage-166 JSON worksheet and stage-170 explicit scenario link,
alongside two copied CPU log files:

    python3 -m tools.foj_stage171_build_identity \
      --bundle ./foj-stage165-gpu-sd-smoke.zip \
      --receipt ./foj-stage171-ci-build-receipt.json \
      --ledger ./private/gpu-observations.json \
      --before ./private/foj-boot-00.txt \
      --after ./private/foj-boot-01.txt \
      --link ./private/cpu-screen-link.json

The tool requires the *provided* ZIP and receipt to match, rechecks
the internal manifest and four binary SHA-256 checksums, and verifies
every **filled** stage-166 build identifier against the receipt.
A wrong commit, run ID or archive SHA-256 is rejected. Missing
metadata never becomes an implicit success: the report says
`operator_build_metadata_missing` or
`operator_build_metadata_incomplete` until all three fields are
provided, whereupon it may say
`operator_recorded_build_identity_matches_receipt`.

Optionally, for a **copied, generated-only research NRO file** taken
from the user's own SD card, add:

    --sd-nro ./sd-copy/foj-deko3d-triangle-research.nro

That file must be a bounded regular NRO, not a symlink, and its
two descriptor-based reads and metadata must agree before its SHA-256
is compared to the archive's triangle NRO. This verifies the *copied
bytes*, not which binary Homebrew Menu actually loaded or executed.
There is no directory scanning, SD mounting, or telemetry collection.

## Report interpretation

A fully consistent local report can say:

    "operator_build_and_visual_claims_consistent_but_unverified"

It always also says:

    "hardware_execution_verified": false
    "gpu_scanout_verified": false
    "original_foj_assets_verified": false
    "switch_gameplay_verified": false

A blank stage-166 build section stays unbound. A blank or
incomplete stage-170 operator link remains unconfirmed. An actual
GPU-displayed frame **cannot be inferred** from a CPU present-call
counter, a correct ZIP checksum, matching visual descriptions, or a
receipt generated by CI.

The source bundle's provenance is generated-only. If the SD user
changes one of the two invented DDS images during the A–E manual
tests, the archive digest is still a reference for the original
research build rather than a digest of the changed SD state.
A same-name copy made later or a different build can only be
compared against the actual new bytes; do not reuse an earlier
receipt without verification.

CI exercises only fabricated NRO/DKSH, synthetic texture checkerboards,
and invented operator descriptions. None of those tests is a physical
Nintendo Switch GPU, PS3 resource or gameplay validation.
