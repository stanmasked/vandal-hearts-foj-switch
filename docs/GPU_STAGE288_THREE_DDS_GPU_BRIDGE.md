# Stage288 — real NeXium GPU proof for the generated Stage286 DDS bridge

**Stacked on:** [Stage287 PR #172](https://github.com/stanmasked/vandal-hearts-foj-switch/pull/172), exact-head successful GCC/Clang [CI #39645832284](https://github.com/stanmasked/vandal-hearts-foj-switch/actions/runs/39645832284).

## Engineering objective

Stage286 established *owner-local* three-slot DDS preparation, where Python validates exactly three file inputs, uses immutable generated FOJRM001 actor/FOJMAT01 material mapping and copies the two UAM DKSH shaders into a private NeXium SD hierarchy. Stage287 independently loaded the same class of data through native C code, including an opaque-rear guard. Stage288 proves that the **Stage286 output**, with unchanged generated geometry, can be loaded by the existing Stage275 research NRO and actually rendered by NeXium's Vulkan backend.

The output is **not** an original-game remaster, original FoJ PS3 material map, real PS3 format validation, proof of the owner's files, or a physical Switch test.

## Fixture and confidentiality boundary

CI invents three tiny 64×64 RGBA8 DDS images from public constants:

| Slot | Public generated color | Alpha | Research meaning |
|---|---|---:|---|
| 0 | (96,72,201) violet | 128 | Translucent near |
| 1 | (232,55,28) warm | 128 | Translucent middle |
| 2 | (21,202,219) cool | 255 | Opaque rear |

A new private directory in GitHub Actions ephemeral **RUNNER_TEMP** contains input DDS, staged SD root, and the local Stage286 SHA-256 binding manifest. The workflow calls Stage286's *actual* `prepare` and `verify` implementations, then launches the real NeXium guest pointed at the resulting SD hierarchy.

The private manifest is **never** copied to `runtime-evidence` or uploaded. The public archive holds only screenshots, NeXium logs, native NRO markers, verified generated-only input receipt and observations containing fingerprints recomputed from the **public synthetic constants**. The original PS3 package, textures and user-provided resources are **never available to this job**. This isolation is intentional: running local private assets in public CI would violate the project's asset-handling policy.

## Acceptance checks

1. Native build: Stage275 deko3d NRO is recompiled on devkitA64; public UAM vertex and fragment DKSH are generated and validated.
2. Host gates: previous Stage273–285 regressions plus 11 Stage288 negative tests and the 21 Stage286 private-staging tests run on the host.
3. Source gate: exactly three generated DDS sources are staged via Stage286, checked against canonical bytes, then SHA-observed **before and after** the guest.
4. True guest gate: NeXium's Vulkan runtime supplies **two distinct actual RGB PNGs** at 1280×720. An independent Stage273 RGB classifier requires expected source-over overlap and opaque rear-only controls with stable material footprints, and a clear-color phase change.
5. Native gate: the NRO, not Python, produces sort witness `FOJ_NATIVE_SORT_V1 2,1,0` and the material/blend/depth receipt `FOJ_NATIVE_ALPHA_PASS_V1 2:0:1:1 1:1:1:0 0:1:1:0`.
6. Provenance gate: the Stage288 independent auditor verifies generated-only receipts and rejects malformed DDS fingerprints, missing native markers, duplicate screenshots, changed pixels, or any accidentally archived Stage286 private binding manifest.

**No artifact is accepted merely because a mock PIL image passes the same classifier.** The actual evidence must be generated by the NeXium job in GitHub Actions and linked to the exact tested commit.

## Next step after Stage288

Once this experiment is green, the **local** owner-private workflow can use the same Stage286 tool for already-compatible DDS, while separate PS3 forensic work establishes whether original assets can legitimately be decoded to those formats. Their results must be measured privately and *never uploaded to the public GitHub repository*.
